# Habitat facts and relationship model

## Review rule

Habitat is not a mutually exclusive animal category. Keep separate relationships for:

- **lives in / habitat** — a place or ecosystem used as home/range;
- **shelters in / home** — a burrow, den, sett, tree cavity, leaf litter or other refuge;
- **feeds in / food source** — where/how it obtains food;
- **moves through / action** — a capability or scene action, not a habitat.

An animal may have several of these relationships and may use multiple environments over its life cycle. The fact wording must say **may**, **some species**, or name a species/context where appropriate. “Air” is not an exclusive habitat; a bird flying above a woodland remains associated with its living/nesting/feeding habitats.

The examples below are a reviewed content shortlist, not production runtime data. English/German sentences are age-targeted drafts and still require native-speaker review before release. Scientific sources establish the fact; they do not establish that a specific illustration visibly depicts it. Any scored prompt additionally requires art/context review.

## Recommended smallest future record shape

Do not build a general content framework during this audit. For a first reviewed future pack, use one small data record per authored relation, conceptually:

```text
AnimalHabitatFact
  animalId                 stable semantic animal ID
  habitatId                stable semantic environment ID
  relationshipType         LIVES_IN | SHELTERS_IN | FEEDS_IN | MOVES_THROUGH
  fact                     explicit EN and DE display/speech text
  speciesScope             optional named species or an explicit broad-group note
  ageSuitability            reviewed band / wording note for ages 5–7
  evidence                  one or more source URLs, access/review date, claim supported
  scoredMatchSuitability    NO | CONTEXT_ONLY | MULTI_VALID, with the matching context ID
```

Use existing `ContentId`, `LocalizedText`/`ContentText`, content versioning and offline repository conventions where they fit. `scoredMatchSuitability` must be an authored decision, not inferred from a relationship record. The record is activity-independent so Explore and later Matching can reference the same reviewed fact without duplicating prose. No new shared schema or source code is introduced here.

## Scored matching rule

A broad relation such as `rabbit → woodland` can have multiple valid contexts. Future Match may ask “Which places could this animal use?” and accept all authored valid answers, or ask a scene-specific question with one answer among choices. Every frozen task must store the accepted answer set/context, not regenerate correctness from one primary habitat. Existing one-category `Sorting` is not suitable for the general relationship model.
